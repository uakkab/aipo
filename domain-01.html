Foundation Layer · Domain 01
Process Maturity
From Tacit Knowledge to Autonomous Automation
Every organization runs on operating knowledge: processes, workflows, policies, and procedures. Most of it lives in people's heads. Before any AI transformation can succeed, that knowledge must move from tacit to documented to practiced to automated. This domain guides that journey.
💡 Core Principle: "Automation does not improve a process. It fixes it in place and runs it faster."
Foundation
Why Process Maturity Matters

The Core Insight

"Automation does not improve a process. It fixes it in place and runs it faster."

If a process is undefined, automation will automate whatever version the implementer happened to observe. If a process is inconsistent, automation will pick one variant and silently retire the others. If the process depends on someone quietly correcting bad inputs, automation removes that person and the corrections with them.

This is not new. Michael Hammer warned about "paving the cow paths" in 1990. What is new: AI lowers the cost of automating something to near zero. Organizations now automate things they would never have formalized before. The prerequisite work therefore matters more in the AI era, not less.

The Four-State Ladder

Operating knowledge moves through four states, one process at a time:

  1. Define it down to every detail, including exceptions
  2. Run it manually as defined, so staff build intuition for where it bends
  3. Automate it under supervision by interviewing people who hold that intuition
  4. Let it run autonomously with limited oversight

⚠️ Skipping a level is the most common cause of failed automation.

Prerequisite
The Readiness Gate: 6 Domains That Must Pass
1

Process

Documented, stable, measured
  • Process exists as a document, not just in people's heads
  • Stable for at least one full business cycle
  • Volume, cost, and error rate known
  • Single named owner accountable
✓ Gate: Documented; stable; volume/cost known; one owner
2

Data

Known, accessible, classified, measured
  • You know where the data is
  • One system wins when data disagrees (source of truth)
  • Machine accessible (APIs, databases, not PDFs)
  • Quality measured for fields automation will use
  • Classified as Public / Internal / Restricted
✓ Gate: Machine-accessible; source of truth; quality measured; classified
3

Structure

Roles, governance, exception handling
  • Roles defined by outcomes, not activities
  • Bridging role exists (tech ↔ operations) with capacity
  • Clear who can approve, pause, rollback
  • Exception path defined: where they land, who picks them up
✓ Gate: Roles framed by outcome; governance decided; exceptions routed
4

Technical

APIs, identity, logging, environments
  • Systems readable/writable programmatically
  • Automations run as scoped identities with audit trails
  • Every action logged with context
  • Non-production environment to test before production
✓ Gate: Reachable via APIs; identity/logging in place; test environment
5

People

Literacy, psychological safety, capacity
  • Baseline AI literacy: what it can and cannot do
  • Psychological safety: reporting problems is rewarded
  • Change capacity: not in the middle of crisis/merger
✓ Gate: Literacy delivered; reporting culture established
6

Measurement

Baseline captured before automation
  • Current state: cycle time, hands-on time, volume, errors, cost
  • Post-automation: exception rate, resolution time, uptime tracked
  • Success measured against baseline, not opinion
✓ Gate: Pre-automation baseline captured
Progression
L0-L4: The Maturity Levels

Once a process passes the readiness gate, it progresses through five maturity levels. Each level is a gate — a process sits at exactly one level and moves right only when the exit criterion is met.

L0: Tacit

Process exists only in people's heads. How it's done varies by person. Output depends entirely on performer.

Exit: Name owner. Have them document it. Move to L1.

L1: Defined

Every step, branch, input, output, and exception is written down. A stranger could theoretically follow it.

Exit: Document survives review by someone who has never done the job.

L2: Practiced ⚠️

This is the level everyone skips, and where most automation fails. Process run as documented for one full cycle. Exceptions known and catalogued. Definition corrected by real use.

Exit: One full cycle run as-defined; exception list stable.

L3: Supervised

Process encoded in automation rules. Machine executes. Human reviews every output. Exceptions routed to human queue.

Exit: Error rate at or below manual baseline for 2-4 weeks.

L4: Autonomous

Machine executes with limited oversight. Humans review samples and exceptions. Most exceptions auto-resolved; novel ones escalated.

Exit: Exception rate and outcomes stable; rollback path tested.

Assessment
Domain 01 Readiness Checklist

Domain 01: Process Maturity is ready when these 4 items are true (PLUS all 6 prerequisite domains pass):

1

Key processes documented

Step-by-step SOPs and decision points. Every step, branch, input, output, and exception written down.

Maps to: L1 Defined minimum

2

Process owners assigned

Each process has a single named owner accountable for its definition, exceptions, and outcomes.

Maps to: L1 Defined minimum

3

Performance baselines established

Current cycle time, error rate, cost, and hands-on time are known. This is the measurement against which automation will be judged.

Maps to: L2 Practiced minimum

4

Exception paths mapped

Not just the happy path. Documented: what happens when inputs are missing, malformed, contradictory, or edge cases.

Maps to: L2 Practiced minimum

🚨 Common Gap Signals: Recognize When You're Not Ready

  • "Tribal knowledge is the primary process documentation" — Only the SMEs know how it really works
  • "Different teams do the same task differently" — No consistency or standardization
  • "No one can describe where a process starts and ends" — Fuzzy boundaries, unclear triggers
  • "Outcomes are measured, but the process producing them is not" — You track results but not the steps
  • "We're not sure what a bad exception looks like" — Edge cases are surprises, not managed
Common Mistakes
Anti-Patterns to Recognize and Avoid

1. Automating to Avoid Defining

"We'll let the AI figure out the process." The AI will figure out a process. It will not be yours, and you will not know what it is.

Fix: Define the process first. Automation is the third step, not the first.

2. Starting with the Hardest Process

The one with the most exceptions, most stakeholders, least documentation. Automating it fails spectacularly.

Fix: Start with the boring one. Learn how automation fails before attempting something interesting.

3. Skipping L2 (The Manual Run)

The temptation is to go straight from a finished document to automation. But L2 is where the document meets reality.

Fix: Run the process as written for one full business cycle. Document what fails. Use that to design automation.

4. Treating Readiness as a One-Time Assessment

Every prerequisite decays. Processes drift, data degrades, owners leave.

Fix: Re-run the gate for each new automation, not once and for all.

5. Tool Procurement Before Process Definition

Buying the platform before the process is defined produces a platform looking for a use case.

Fix: Define, practice, measure. Then decide on tools. Not the other way around.

6. Letting the Vendor Define Exception Thresholds

The point at which an automation should hand off to a human is a business decision. Defaults are set for the vendor's typical customer, not you.

Fix: You decide when exceptions escape to humans. This is a governance decision, not technical.

Next Steps

  1. Self-assess: Use the 4-item checklist above. Which items do you have?
  2. Assess readiness: Do all six prerequisite domains pass? Which is the biggest gap?
  3. Place your process: Use the L0-L4 matrix. Where does your process sit today?
  4. Plan the next level: What does the exit criterion for your next level require?
  5. Work the lowest row first: Across the matrix, which row has the biggest gap?
